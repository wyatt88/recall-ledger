## 1. 需要分开回答的三个问题

1. **机制：**给定同样已经识别的事实、条件、纠正目标和依赖，RecallLedger 是否更可靠地维护当前有效依据？
2. **产品：**同一真实 Agent 获得相同原始历史与资源时，接入后是否更能完成任务，并且成本、等待和维护可接受？
3. **迁移：**更换宿主或搬迁部署后，目标 Agent 的任务能力相对目标端持续使用的参照损失多少？

第一个通过不能替代第二个；数据逐字保持不能替代第三个。需要报告效应大小、区间与失败案例，不能只给“显著更好”或一个混合总分。

当前最有判别力的风险是：strict evidence 通过保留完整原文与元数据避免该表示路径的生成性改写，但它不压缩语义，预算不足会拒绝。因此需要验证的不是“能否保存原文”，而是**在有限上下文、有限维护预算与真实热会话中，能否及时提供足够且当前的证据，改善行动**。

## 2. 强基线与两条轨道

### A 轨：受控机制

所有组共享固定 Agent 读者、上下文构造器、工具、模型版本、token 计数器和资源上限；输入同一准入事件流。事实键、时效、纠正映射和完整已知依赖如由评测器提供，必须提供给所有组，并明确排除提取能力的结论。

| 组别 | 最低能力 | 用途 |
| --- | --- | --- |
| 无长期记忆 | 当前任务输入与当前会话的统一预算 | 负控，检查任务是否根本不需要记忆 |
| 强原文检索 | 全部合法原始来源、词法/向量混合检索、当前版本与撤回过滤、相同上下文预算 | 排除“只是保存更多信息”的解释 |
| 简单来源重建 | 强原文检索，加完整条件传递与按需从合法原文重建；与 RecallLedger 同等声明的依赖/纠正输入 | 检验复杂生命周期与增量维护的额外价值 |
| 递归摘要 | 来源存档不删除，明确的摘要预算、更新和纠错策略 | 量化递归改写风险；不可故意只留旧摘要且不给搜索原文 |
| RecallLedger strict evidence | 当前默认完整原文胶囊、依赖守卫、失效与修复 | 主实验系统 |
| RecallLedger model summary | 显式启用模型摘要；计入生成与修复费用 | 区分工程一致性和语义压缩策略 |

全历史在同一预算内能装下时增加长上下文参考；超过预算的长上下文结果单列资源曲线。不得给 RecallLedger 原文回溯而让对手只有摘要，也不得要求对手使用明显落后的检索参数。

### B 轨：真实宿主完整系统

按每个宿主版本分别比较：

1. 原生推荐/最佳实践配置，包括实际支持的搜索、更新、压缩、召回与刷新。
2. 同一宿主接入 RecallLedger 后的配置。
3. 宿主不能关闭原生记忆时，明确标为“原生 + RecallLedger”，不称替换原生。

原生 MD 文件只是一个实现载体，不能自动视为静态、无检索或无治理。先核对宿主真正读写、缓存、检索、更新的路径；有不可观察部分时记为未知。接入难以做到独占时，不能从增量组推导 RecallLedger 单独的能力。

B 轨只提供相同原话、文件、环境与事件到达顺序。提取、事实键、指代/否定识别、准入、依赖捕获、人力及失败重试全部在被测系统内。禁止把评分器真值变成 RecallLedger 的结构化输入。长期 pending 或停用召回不能凭零错误获胜。

两种预算视角均需报告：

- **公平归因点：**相同最终读者 token 上限、总模型/资源预算与截止时间，比较效果；输入不同则记录实际消耗。
- **实际部署曲线：**各组在冻结的多个预算档位内自行选择合理配置，报告效果—延迟—总成本的前沿。预算档位与调优费用对称，不选其中唯一有利档位。

固定预算不意味着让两套系统强行调用相同次数。少调用本身可构成成本收益，但任务成功、覆盖与恢复仍需达标。

## 3. 纵向设计：历史是样本单位，检查点不是

每条独立项目历史包括稳定事实、时效/条件、纠正、撤回、派生引用、干扰、跨会话任务。项目/用户及其来源模板按簇切分，不能把同一模板的数值替换分别放入开发集和封存集。

每条历史在所有组中配对回放；运行顺序随机交错，随机种子嵌套在历史内。受控轨冻结完整输入历史，包括助手事件，避免前序不同输出导致后续输入不再相同。自然闭环交互另作系统级实验，保留因交互轨迹变化引起的全部成本和失败。

预先固定检查点与三个独立压力轴：

- 可访问历史长度。
- 宿主压缩次数。
- 派生表示深度。

不能把三者同时变大后将损失全归因于“摘要代数”。先做独立轴的最小对照，再做联合压力测试。日历时间不是这些轴的替代量；加速 1,000 次修订不是使用了数年。

同一时点复制隔离状态，分别测试冷会话、已经看到旧值的热会话、压缩后恢复、进程重启。探测只读或使用副本，问题、答案、评分和修复诊断不得回写主历史。不要只清空 RecallLedger 组旧上下文。

建议主要纵向估计量：

- 每条历史的末段有效任务成功率配对差。
- 每条历史“末段 − 初段”的变化，再计算两组变化的差（退化差）。
- 稳定事实、纠正/撤回、条件性事实分层的覆盖和误用曲线。
- 固定检查点权重下的曲线面积，作预定次指标；不能事后选择最有利检查点。

“两组都下降但 RecallLedger 少下降”与“RecallLedger 在容差内不退化”是两个主张，要分别给区间。新知识覆盖下降也不能被旧事实哨兵仍保存所掩盖。

## 4. 迁移设计：固定目的端，分三类操作

分别验收：

1. 多宿主共用同一个 ledger，仅切换客户端。
2. 一个 RecallLedger 部署向另一个部署导出/导入。
3. 原生品牌记忆格式导入 RecallLedger 再交给另一品牌。

不支持的格式记为未支持，并报告它对目标使用范围的影响；不虚构支持，也不把一个格式未支持算成所有任务答错。

对每条历史和每个目标端 B，固定 B 的模型、提示、工具、环境、后续任务与总预算，配对：

| 条件 | 含义 |
| --- | --- |
| A → B | 经待测迁移流程，在 B 执行后续任务 |
| B continuous | 同样的冻结前史从起点进入 B，使用对应的记忆配置 |
| B empty | B 没有历史记忆，量化知识价值 |
| B sufficient evidence | 评分器提供合法充分的原始依据，不能含最终答案；只用于诊断 |
| 原生最佳可行迁移 | 使用宿主实际提供的导出、来源重放或官方交接，记录人力与损失 |

迁移主效应是同一 B 中 `A → B − B continuous` 的历史级配对任务成功差。不能比较 A 迁移前分数与 B 迁移后分数，因为模型和宿主已经变化。比较两种记忆系统的迁移能力，可进一步比较各自的迁移损失，但同时报告各组 continuous 的绝对质量，防止低基准掩盖低损失。

记录切换开始→首次有效任务、固定期限内后续任务成功、人工重新解释分钟/信息量、导出/导入/索引重建/重新绑定的完整费用与停机。

**当前工程特殊项：**portable bundle 不传 executable recipes；导入胶囊在目标端 `verified=false / no_local_evidence_recipe`。需在目标端明确重建本地 recipe。重建、再次证明当前来源、补齐向量等时间与费用应在 A → B 中入账，不能提前为迁移组免费完成。未经目标端重新验证，不能把来源标签或原有 JSON 的验证字段当作目标端认证。

B 再进行纠正、撤回后执行 A → B → A，检查有效读取、pending 状态、不复活撤回数据、重复导入及并发分支拒绝。数据层检查与行为层检查各自报告。

## 5. Coverage–risk–cost：不能靠拒答取得零失真

所有主要指标保留超时、缺失、拒绝与恢复失败；不可只统计系统愿意回答的子集。

| 指标 | 分母 / 定义 | 防止什么误判 |
| --- | --- | --- |
| 有效任务成功 | 全部指定任务；正确行动且无当前版本、作用域或许可违规，在统一期限内完成 | 空输出、超时仍留分母 |
| 合法充分证据覆盖 | 真值判定可回答的任务；送到读者的证据足以完成任务且保留必要条件 | 不是命中任意相关文本 |
| 选择性行动风险 | 实际采取行动的任务中，错误/无依据/陈旧行动比例 | 必须同时报告行动覆盖，不能单独排名 |
| 不必要拒答 | 有充分合法依据的任务中，拒答或未完成的比例 | 防止过度守卫 |
| 正确拒答 | 无充分合法依据的任务中，恰当拒绝或请求缺失信息的比例 | 撤回后没有别的依据可以拒绝 |
| 陈旧记忆误用 | 预先指定的旧事实诱导任务中，最终答案/行动使用旧值作为当前值 | 合法历史问答不算陈旧误用 |
| 撤回暴露 | 提交确认后开始的当前读取中，暴露不合格正文的比例 | 与宿主早先已见旧信息区分 |
| 无关记忆保留 | 未受纠正/撤回影响、仍可回答的任务中，证据与任务成功保留 | 防止“删掉一切”看似修复 |
| 条件丢失 / 无依据新增 | 隐藏评分器对比事件真值与实际 delivered context、行动；分阶段记录 | 原文保存不等于条件被读者遵守 |

按冻结阈值画风险—覆盖曲线、成功—成本曲线以及恢复时间分布。当前 strict evidence 因完整胶囊超预算而失败时，应记录“来源存在，但当前预算下未能提供足够证据”；不可记为原文不存在，也不能从有效任务分母删除。

成本至少拆分初建、提取/准入、嵌入/检索/重排、压缩、失效/修复、目标读者行动、失败/重试/取消、人力。保留原始 token、CPU/GPU 时间、峰值 RSS、磁盘/WAL/向量增长、等待时间与货币假设。

每有效成功任务成本使用**所有任务总成本 / 有效成功数**，成功为零时无有限值。研究调优/裁判费用单列，但计入项目总预算。效果相同且更慢、更贵时，工程安全能力不能被包装成总性能优势。

两个恢复时钟：

1. 原始纠正到达→能再次完成受影响任务，包含识别与准入。
2. 已准入提交确认→后续读取不返回旧正文，以及→重新提供合法充分证据。

未恢复样本按右删失处理并报告未恢复比例；不能只对恢复成功样本取平均。冻结观察窗内可报告限制平均未恢复时间；不给无限长的无期限“最终恢复”。

## 6. 性能归因：微基准和真实任务分开

存储微基准固定硬件、数据规模、索引状态、返回有效证据量、并发与读写比。分别冷启动/热缓存、空闲/维护竞争、单请求/并发；同时报告失败率、有效吞吐、p50/p95 与资源。不用返回空结果更快的系统与返回充分证据的系统直接比较查询延迟。

原生黑盒 App 无存储接口时，仅报告端到端时间；不能把 RecallLedger 的进程内 SQLite 耗时与原生 App 的整轮模型耗时相除。Rust 与 Python、SQLite 与向量库的语言/存储差别要通过独立实现对照归因，不从语言直接推出效果。

端到端计时包含请求排队、工具调用、上下文拼接、模型、维护争用和真实行动。字符预算不能假装 tokenizer-exact：记录交给固定读者的完整序列化内容及实际 token 数。所有组使用统一最终上下文上限，超限按冻结规则失败或截取，不能偏袒某一组。

小样本不稳定的 p99 只作探索。即使有大量请求，也应按独立运行/历史簇给不确定性，而非把相邻请求当独立样本。

## 7. 样本量、统计与承诺边界

**30 条开发历史只适合发现管线错误、校准判据和估计方差，不足以预先宣称有效。** 封存集的样本量需结合目标差异、历史内相关、配对差的方差、重试与多重比较再冻结。

令每条独立历史的配对成功率差为 `d_j`，其开发集标准差估计为 `s_d`。两侧 5% 显著性、约 80% 功效的粗略正态近似：

`n ≈ ((1.96 + 0.84) × s_d / 目标绝对差异)^2`

仅为算量示例，假设 `s_d = 0.25`：

| 独立历史数 | 粗略可检测绝对差异 |
| --- | --- |
| 30 | 约 12.8 个百分点 |
| 100 | 约 7.0 个百分点 |
| 200 | 约 5.0 个百分点 |
| 500 | 约 3.1 个百分点 |

这不是该系统的实测方差、最终功效计算或预算授权。有效样本单位是独立历史；同一历史的 100 次问题/检查点不会把 30 条历史变成 3,000 个独立样本。随机种子重复可降低测量噪声，不能替代覆盖更多项目。

非劣性比“未观察到显著下降”要求更强。应冻结可接受下降 `δ`，并要求配对成功差的置信下界高于 `−δ`。没有显著差异不能证明不退化。以上 `s_d=0.25`、真实差为零的近似下，3 个百分点边界约需 545 条独立历史，1 个百分点约需 4,900 条；真实设计、分布、缺失、端点与多重性都会改变这个数。

初版建议只选一个主要宿主、一个最强主要对手和一个主要成功指标。长期陈旧风险、覆盖、成本设为预定次指标/门槛。若要同时声称多个宿主、多个基准都优于，应处理多重比较（例如预定层级检验或 Holm）；不能在十项比较中挑一次显著。

主要分析按历史簇配对 bootstrap 或预定的簇级差异模型；保留配对、反事实家族与重复结构。历史长度差异大时，预先选择“每项目等权”的主估计量，同时报告“每任务等权”的次估计量，防止长历史支配结果。二元单任务配对可用 McNemar 等方法，但不能无视同一项目重复任务的簇相关。

对撤回复活/跨域暴露等高严重性事件，可把任何经独立复核的违规设为工程阻断。零观测不等于零风险：若事件真独立、同分布，0/n 的单侧 95% 上界近似 `3/n`；重复同模板的事件不满足此假设，不应借巨大循环数宣称罕见风险已得到该上界。

先做开发校准，再封存协议与测试集后单次验证；查看验证结果后调参所得新成绩是探索。追加测试需新封存集或预先规定的序贯规则，不能不断看结果直到显著。

## 8. 必要消融和反证

至少覆盖：

- 完整来源存档相同，比较按需重建与持续增量修复。
- 检索、失效与条件传递相同，比较原文胶囊和模型摘要。
- 治理相同，比较词法/向量/混合检索。
- Memory 相同，比较仅 MCP 按需调用和宿主完整生命周期接入。
- 依赖记录完整与刻意遗漏，量化已知依赖机制对隐藏影响的边界。
- 稳定历史与全局变化历史，检验增量维护何时得不偿失。

关闭撤回校验的版本只作隔离负控，不能作为“业界原生”代表。重建组的全部成本要计入，增量组长期维护也要计入。

下列观察足以否定或缩小优势主张：

1. 强原生或简单原文重建组在冻结主要任务上达到相同/更高质量，并且成本和延迟更低：不能宣称 RecallLedger 的整体优势。
2. 陈旧错误减少，但有效证据覆盖/任务成功下降超出冻结容差：不能宣称更好的长期记忆。
3. 收益只发生在额外原文、人工真值、更多 token/模型调用或只清空自身热会话的条件：否定记忆机制归因。
4. 胶囊来源逐字正确，但 Agent 经常违反条件或继续使用已经进入热上下文的旧值：工程契约成立不等于产品问题解决。
5. 同预算下大来源胶囊反复超限，产生积压/拒答，按需重建组无此问题：需调整表示/调度；不能把拒绝计为效果成功。
6. A → B 相对 B continuous 的任务损失超界，或靠大量人工重述才恢复：跨品牌连续性目标未达标。
7. A → B → A 使撤回事实复活、pending 自动接受或来源作用域错误：迁移工程验收失败，无论平均 QA 分数多高。
8. 只在合成纠正链优势明显，对公开独立集、实际宿主或良性任务无收益：限定适用场景，不外推“最强记忆框架”。

## 9. 进入执行前的最低交付

- 冻结宿主/模型/适配器/数据/评分器与 token 计数版本。
- 基线能力清单及其配置人复核记录。
- 封存事件与独立 gold；确认未来事件、答案、评分反馈不可见。
- 每个系统每个历史的隔离运行、成本账、失败账和实际送入读者的上下文。
- 可重复的三种状态探针：持久化状态、delivered context、实际行动。
- 预定预算、截止、样本量依据、统计与停止规则；由另一岗位审阅。
