# Native Memory 与 RecallLedger：反方审查

日期：2026-10-13，Asia/Shanghai。岗位：魏慎言，独立审稿人 / 反方专家（AI 岗位）。

**审查性质：proposal review；不是实验验收。** 仅审阅本目录 `PROTOCOL.md`、`EVALUATION-REVIEW.md` 与岗位职责；本次没有运行模型、真实 Host、竞品或性能测试，没有重审全部 Rust 源码。本记录针对收到的主协议文本；后续主协议若吸收建议，应保留本次意见与处理说明。

## 结论

**可继续形成测试 Harness，正式比较前需修改/冻结下列口径。** 协议已经明确强基线、来源与行为的区别、hot session、拒答分母、原文保真超限、独立历史簇和非劣性条件，没有发现必须推翻整体方案的问题。

最重要的两项是：**受控 MD 与真实 Native 必须使用不同配置标识；迁移必须加入 Native 的实际 A→B 过程。** 未补齐时，实验仍可产生有效的局部结果，但不能分别推出“优于真实 Native”和“迁移优于 Native”的结论。其余三项属于执行前必须落实的可观测合同，当前未执行，不能断言已发生泄漏、漏算或偏袒。

严重程度：P1 为阻断相应比较结论；P2 为限制解释或需要在冻结时补齐。这里的严重程度不表示线上缺陷或已观察到违规。

## 1. P1：受控 MD 与真实 Native 的配置身份有混用空间

**原段落：**

- 主协议 §2：“Controlled Harness 中的 MD 基线叫‘受控 MD backend’，不能称为某厂商真实 Native Memory。”
- 同节对照表却只定义 `N2：Native tuned`，含义为实际产品官方支持机制。
- §8 的 smoke 将 `N0/N2/R0/L` 作为同一个四配置集合；胜出条件也统一写“相对 N2/R0”。

**问题与最强反对：**两条 Track 的原则正确，但运行配置和结果标签尚未把它落实。如果受控 runner 用自写 MD 实现填入 `N2`，最后报表很容易把受控基线误称为原生记忆。反之，将真实 Native API 拼进固定 reader 的受控 Track，也可能改写该产品正常的读写与压缩机制。得到的是不同实验对象。

**具体修订：**

1. 受控组使用独立 ID，例如 `C0 / C_MD / C_RAW / C_LIFECYCLE / C_LEDGER`；真实 Host 使用 `H_NATIVE_DEFAULT / H_NATIVE_TUNED / H_LEDGER_ONLY / H_NATIVE_PLUS_LEDGER`。
2. `systems.lock.json` 强制包含 `track`、`host_id`、`memory_configuration`、是否可关闭原生记忆、读写路径与观察能力。
3. 将 smoke 标明究竟先跑哪条 Track；缺乏真实 Native 接口时只跑受控开发验证，不用代用品补成真实 Host 格。
4. 胜出条件分别定义为“机制净收益”与“该 Host 上的完整配置收益”；不能在一个表中替换对手身份。

**最低通过条件：**同一个配置 ID 只对应一种 Track 和实现；原生标签都能链接到实际产品版本与资格检查记录。

## 2. P1：迁移主要对照缺少 Native 的实际迁移流程

**原段落：**

- 主协议 §7 Migration：`A→B / B continuous / B Native / B empty / B sufficient evidence`。
- 评估审阅 §4 已另列“原生最佳可行迁移”，但主协议尚未将其列为需执行的比较格。

**问题与最强反对：**`L 的 A→B − L 的 B continuous` 可以测量 RecallLedger 自己的迁移损失；`L 的 A→B − B Native continuous` 混合了 Memory 配置与迁移处理。两者都不能单独回答“是否比原生迁移更容易恢复工作”。原生导出、复制工作目录或重放来源也可能达到同等连续性。

**具体修订：**

- 对同一个 A、B 和冻结前史，至少并列：
  - `L: A→B` 与 `L: B continuous`；
  - `Native best feasible: A→B` 与 `Native: B continuous`。
- 每套方案同时报告目的端绝对成功率、自己的迁移损失、恢复等待与重新解释成本；可把两套迁移损失之差作为附加估计量，不能只报该差值而隐藏低 continuous 分数。
- 若原生没有导出，允许已冻结的正常替代流程；将不支持、需要人工重新输入、迁移失败三种情况分别记录。不要只挑能自动迁移的案例算平均值，也不要把格式不支持伪装成每个任务语义错误。
- “同一 ledger 换客户端”“两部署 bundle”“Native 格式导入”分别比较，不以最简单的第一种替代另外两种。

**最低通过条件：**每个“迁移优于原生”的主张都有同一 A→B 配对的 Native 流程、成本与后续任务结果。做不到时只能报告自身迁移保留率和能力缺口。

## 3. P1（执行前）：gold 隔离需要访问边界与负向检查

**原段落：**主协议 §3 规定 gold 不进入 Agent 文件、Memory、检索库或工具响应；§9 拟保存 `public-events.jsonl`、隔离 `gold`、trace、grader。评估审阅 §9 要确认未来事件、答案和评分反馈不可见。

**问题与最强反对：**原则已经完整，但“放到另一个目录”不足以隔离具有 shell/文件搜索权限的本地 Agent。封存答案、未来事件、评分器源码、测试错误或别组 trace 仍可能进入工具路径。若一组能读到而另一组不能，所谓记忆增益不可解释。本轮没有检查实际执行环境，因此这是冻结门槛，不是已发现泄漏。

**具体修订：**

1. 评分器运行在被测 Agent 不可访问的进程/容器/账户边界；只挂载该时刻已公开的事件和任务材料。
2. 封存材料、未来事件、其他配置/分支 trace、诊断副本和评分日志不得位于 Agent 可读父目录、共享索引、环境变量或网络接口中。
3. 为每个 Host 做访问资格检查：用专门的无害 canary，证明正常文件、搜索与 shell 工具不能读取评分区或未来事件；同时保存公开输入 manifest。
4. 主检查点的 hidden verifier 在任务结束后评分，结果不返回主历史。Agent 正常可运行的公开测试与隐藏评分器分开；禁止隐藏失败消息意外暴露目标值。

**最低通过条件：**资格检查有实际执行证据，且输入 manifest 能逐时点说明可见内容。隔离能力不可证实时，该 Host 结果只能降为探索。

## 4. P1（执行前）：全路径预算与超限处理必须固定，不能由 runner 临场决定

**原段落：**

- 主协议 §6 要统计读者实际收到的全部 Memory 内容，指出 `max_chars` 不是 token 口径。
- §3/§8 将大来源闭包和原文保真预算拒绝纳入测试。
- 评估审阅 §6 写“超限按冻结规则失败或截取”。

**问题与最强反对：**RecallLedger 完整来源胶囊比一段摘要大，这是要测的关键取舍。“失败或截取”尚未选定；截取若恰好保留答案、剔除约束，或者仅对某一组做 query-aware 选择，会改变系统本身。另一个风险是只限制初始 Memory 块，但允许后续工具逐次读取来源而不计入 Memory/总 token 上限。

**具体修订：**

- 冻结整个任务的累计资源预算与每个 reader 调用的上下文上限。后续 `read file`、搜索、工具返回、来源回溯也按实际输入计量，不能通过改名避开预算。
- 逐组锁定 overflow 策略：原生截断、分页、重新检索、压缩或明确失败。补救过程是被测方案的一部分，记录其调用和成本；评测器不能在观察 gold 后帮忙挑内容。
- 对 strict evidence 保留完整合同：不由 runner 静默删掉 capsule 的来源/条件来使其通过。若评测另一种节选策略，给独立配置 ID。
- 同时统计“来源存在但未能送达”“送达不充分”“语义/行动错误”，并把失败、超时、拒绝保留在任务分母。

**最低通过条件：**同一序列化 trace 能重算总 token，超限决策不依赖 gold，且各组的 fallback 是预注册并真实执行的。

## 5. P2：后台尾部工作与成本截止需要结算规则

**原段落：**主协议 §6 计入所有前后台工作、失败和重试；§4 从事件可见开始计算恢复；§9 按事件 ID 关联后台任务。现阶段未明确任务截止后仍运行的 repair/embedding 如何结算。

**问题与最强反对：**不能在主任务截止时截断账本，把尚在运行的 maintenance 留到窗外；也不能让下一次 checkpoint 免费使用上次未计费的修复。相反，无期限等队列清空会让观察窗不一致。两种错误都可能改变速度和成本排名。

**具体修订：**

- 预先区分“用户成功截止”和“资源结算截止”；成功必须在前者完成，已启动工作在后者记录实际完成/取消与资源。
- 留存跨检查点的 job ID、起止时刻、上游事件、账单归属与未结算状态，连续回放不重复收取同一 job。
- 硬预算终止后取消能取消的工作；无法观测或取消的远端消耗标未知/下界，不能报为精确总成本。
- 若 maintenance 作为持续后台常驻服务运行，明确整段前史与空闲维护的计量边界，并报告未摊销总量。

**最低通过条件：**所有已启动后台 job 在账本中有归属和终态，或明确列为未结算；不存在跨窗免费完成。

### 最终文字复核：第 4 项关项

再次读取主协议 §6，已确认新增规则同时覆盖：

- 后续文件读取、search 与 tool response 的来源回溯计入每次 reader 的实际输入和累计任务预算；
- 每组 overflow/fallback 在开发集后冻结，补救行为显式命名与记账；
- runner 不读取 gold 选择片段，不得静默去掉 strict capsule 的条件后仍称完整 verified evidence。

因此第 4 项在**提案设计层已解决**。本次提出的五项意见均已有明确设计处理；没有剩余的文字层阻断项，允许进入 Harness 实现与开发集校准。gold 隔离、全路径计量、后台结算、真实 Host 准入和正式统计协议仍须实施、冻结并提供运行证据；此次关项不构成实验通过、真实产品验收或 RecallLedger 优势证明。
